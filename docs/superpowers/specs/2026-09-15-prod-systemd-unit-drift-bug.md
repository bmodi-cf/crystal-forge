# Production host runs an orphaned systemd unit — bug

**Date:** 2026-09-15
**Status:** reported, awaiting fix
**Severity:** high — production has no database backups and no Postgres start guard
**Affects:** PRODUCTION host (`automationPROD`) only. The pilot is not known to be affected; verify separately.

## Summary

The production dashboard is running a systemd unit that was generated by a script
which no longer exists in the repo. `deploy/install.sh` — the supported installer
that replaced it — has never been run on that host. Two of the three units the
repo ships are therefore absent, and the one that is installed predates the
Postgres start guard.

The concrete consequences, in order of how much they would hurt:

1. **There are no database backups on production.** `crystal-forge-backup.timer`
   is not installed, no systemd timer of any kind exists on the host, and
   `/var/backups/crystal-forge` has never been created. The dashboard DB and every
   forge DB are currently unprotected against a bad restore, a dropped table, or
   disk loss.
2. **An unplanned reboot brings the dashboard up against a dead database.** The
   installed unit has no `ExecStartPre=/usr/local/bin/crystal-forge-ensure-postgres`,
   and `docker-compose.yml` deliberately gives `postgres` no restart policy.
3. **The unit is unmanaged.** Its own header points at a script that was deleted,
   so the next person to follow that instruction has nothing to run, and any
   edit is invisible to the repo.

## How it was found

While bringing production up to `origin/dev` on 2026-09-15, a question about where
`ExecStartPre` was defined led to comparing the installed unit against
`deploy/systemd/crystal-forge.service`. They are different files with different
`ExecStart` lines.

## Evidence

Measured on the production host, 2026-09-15. Re-check before assuming any of it
still holds.

| Check | Result |
|---|---|
| Installed unit header | `# Managed by create-forge-systemd.sh — re-run that script to regenerate.` |
| `create-forge-systemd.sh` in repo | Absent. Deleted in `df0479f` ("feat(ops): unified systemd installer + Postgres start guard"). |
| `systemctl list-unit-files 'crystal-forge*'` | `crystal-forge.service` only — 1 unit file listed |
| `systemctl list-timers 'crystal-forge*' --all` | 0 timers listed |
| `/usr/local/bin/crystal-forge-dashboard` | absent |
| `/usr/local/bin/crystal-forge-ensure-postgres` | absent |
| `/etc/default/crystal-forge` | absent |
| `/var/backups/crystal-forge` | absent — no backup has ever run |
| `docker-compose.yml` `postgres:` | no `restart:` key (only `registry` has `restart: unless-stopped`) |

### Installed vs. shipped

| | Installed on prod | `deploy/systemd/crystal-forge.service` |
|---|---|---|
| Postgres guard | *(none)* | `ExecStartPre=/usr/local/bin/crystal-forge-ensure-postgres` |
| Build step | inline `… /next/dist/bin/next build` | `ExecStartPre=/usr/local/bin/crystal-forge-dashboard build` |
| Serve step | inline `… /tsx/dist/cli.mjs … /server.ts` | `ExecStart=/usr/local/bin/crystal-forge-dashboard serve` |
| Per-machine config | inline `Environment=` lines | `EnvironmentFile=/etc/default/crystal-forge` |
| `Wants=` | `network-online.target` | `network-online.target docker.service` |

The inline values currently baked into the installed unit, which must be carried
across to `/etc/default/crystal-forge`:

```
User=bmodi
WorkingDirectory=/home/bmodi/work/crystal-forge
NODE_ENV=production
PORT=3030
PATH=/home/bmodi/.nvm/versions/node/v24.18.0/bin:...
```

Note `deploy/crystal-forge.env.example` still shows `NODE_BIN_DIR=.../v24.16.0/bin`;
production runs **v24.18.0**. The installer fills this from the host it runs on,
so this resolves itself — but a hand-written config file would get it wrong.

## Root cause

`df0479f` replaced an ad-hoc unit generator with `deploy/install.sh` plus checked-in
unit files. The pilot presumably picked this up as part of normal development. The
production host was provisioned before that commit and nothing re-ran the installer
there, so it kept the pre-`df0479f` unit indefinitely. Nothing in the deploy flow
detects or reports the drift.

## Why it hasn't bitten yet

`crystal-forge-pg` has been up 3 weeks continuously, so the missing guard has had
no reboot to fail on. The missing backups produce no symptom at all until the day
one is needed. Both defects are silent by construction, which is the argument for
fixing them before the next unplanned restart rather than after.

The failure mode is not hypothetical: `scripts/ensure-postgres.sh` records it
happening on 2026-07-28 — the dashboard came up on a dead DB and every request
failed with Prisma `DatabaseNotReachable`. That incident is why the guard exists.

## Proposed fix

Run the supported installer on production, as the checkout owner (not under sudo):

```
cd /home/bmodi/work/crystal-forge
./deploy/install.sh --print     # review; changes nothing
./deploy/install.sh             # installs both units, enables, restarts
```

The installer is idempotent, backs the existing unit up to
`<unit>.bak-<timestamp>`, and writes `/etc/default/crystal-forge{,-backup}` once
without clobbering them afterwards. Rollback is documented in its header.

Then take the first backup explicitly rather than waiting for 02:30:

```
./deploy/install.sh --backup --run-now
```

### Points to get right

- **Run it as `bmodi`, never under sudo.** As root it resolves root's Node (often
  an old system one) and bakes `User=root` into the unit. It calls sudo itself for
  the privileged steps, and refuses to start if `EUID` is 0.
- **Expect ~1-2 min of downtime** on the restart — `ExecStartPre` rebuilds from the
  working tree.
- **Confirm `NODE_BIN_DIR` lands on v24.18.0** in the generated
  `/etc/default/crystal-forge`, matching what the current unit's `PATH` pins.
- **Budget disk for backups** — the example config notes ~3 GB steady-state at the
  default GFS retention (31d / 183d / 730d).
- Migrations stay manual by design; `ensure-postgres` deliberately does not run
  `prisma migrate deploy`, so this changes nothing about the upgrade procedure.

## Verification

After the fix:

```
systemctl list-unit-files 'crystal-forge*'        # expect 3: service, backup.service, backup.timer
systemctl list-timers 'crystal-forge*' --all      # expect the 02:30 timer, NEXT populated
systemctl status crystal-forge.service            # active; both ExecStartPre lines exited 0
ls -la /var/backups/crystal-forge                 # expect an archive after --run-now
```

Reboot-safety is the real acceptance test and cannot be proven without a reboot.
If one can be scheduled, the check is that the dashboard serves 200s afterwards
with no manual `forge-launch.sh` run.

## Out of scope

- Changing the backup retention tiers or `BACKUP_ROOT`.
- Auditing the pilot host for the same drift — likely worth doing, tracked separately.
- Adding drift detection so a host running a stale unit reports itself. Worth
  considering; it is the reason this went unnoticed for weeks.
